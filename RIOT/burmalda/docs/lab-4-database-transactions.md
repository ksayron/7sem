# ЛР 4: PostgreSQL, общий ресурс, транзакция и сага

## Запуск и демонстрация

```powershell
# Docker Desktop должен быть запущен. 5547 свободен на проверенной машине;
# порт 5432 занят PostgreSQL другого проекта.
./tools/Start-Lab.ps1 -PostgresPort 5547 -Full
# Остановить только процессы, запущенные этим скриптом:
./tools/Stop-Lab.ps1
```

Открыть `http://localhost:5300/concurrency-lab`. Без `-Full` запускаются только лаборатория, gateway и клиент; `-Full` также запускает все сервисы предметной области для настоящей Lending Saga. Скрипт сохраняет журналы в `.artifacts/lab-runtime/`. Для интерактивной цветной консоли можно запустить отдельный API через `dotnet run --project ...` с `ConnectionStrings__Database`, указывающим выбранный порт. Нельзя одновременно запускать второй экземпляр на том же порту.

Инициализация существующего Docker volume выполняется идемпотентным `init-databases.sh`: создаётся недостающая учебная БД, существующие данные сохраняются. Пароли в appsettings — локальные значения из проекта; пользовательские подключения задаются через `ConnectionStrings__Database`.

1. Выбрать **Без lock** и запустить: два SUCCESS, две выдачи единственного экземпляра. Барьер после чтения делает ошибку воспроизводимой.
2. Выбрать **lock**: один SUCCESS, один FAIL; в БД одна выдача. В журнале видны START, WAIT LOCK, LOCK, CHECK, результат и UNLOCK.
3. Кнопка **Сравнить 4 опыта транзакции** выполняет без общей транзакции / с общей транзакцией, с ошибкой / без ошибки. Для каждого опыта создаётся собственный ресурс.
4. **Транзакция → После создания выдачи**: BEGIN → OPERATION 1 → ERROR → ROLLBACK; выдач 0, книга свободна. **Перед COMMIT** проверяет отмену после обоих изменений.
5. **Сага**: создать опыт и нажимать «Следующий шаг». При успехе шаги ReserveBookCopy → ReservePoints → CreateLoan. Отказ Economy освобождает книгу; отказ Lending сначала снимает резерв BD, затем освобождает книгу.
6. Скачать JSON; открыть подробный журнал или нужную строку истории. Для проверки двумя независимыми вкладками использовать блок «Два отдельных клиента», общий ID и разные ClientId. После создания общего опыта автоматическую кнопку запуска использовать не нужно.

## Архитектура и данные

Сохраняется `Blazor Client → YARP Gateway → ConcurrencyLab API → PostgreSQL`. Клиент не получает строку подключения и не обращается к БД напрямую. PostgreSQL выбран как уже используемая СУБД Burmalda: реляционная модель, внешние ключи, ограничения и реальные локальные транзакции подходят для связанных сущностей и сравнения атомарности. Для unit-тестов используется SQLite; отдельные HTTP-опыты подтверждают поведение PostgreSQL.

Один PostgreSQL контейнер содержит отдельную `concurrency_lab_db`, принадлежащую роли `concurrency_lab_app`. Учебные данные не хранятся в БД Catalog, Economy или Lending. Предметная область прежняя: выдача физического экземпляра книги и резерв баллов BD.

| Таблица | Поля PostgreSQL | Ограничения |
|---|---|---|
| `lab_copies` | `Id uuid`, `Title varchar(200)`, `Available boolean`, `ReservedPoints integer` | PK Id; NOT NULL; CHECK ReservedPoints >= 0 |
| `lab_loans` | `Id uuid`, `CopyId uuid`, `ClientId varchar(32)` | PK Id; FK CopyId → lab_copies.Id, ON DELETE CASCADE; NOT NULL |

Две строки выдач на один CopyId намеренно разрешены схемой учебной БД для демонстрации Unsafe. Корректность в режиме lock обеспечивает защищённая операция проверки и резервирования. Производственный Catalog использует собственные механизмы условной записи; учебный код их не заменяет.

`POST /api/concurrency-lab/database/runs` создаёт экземпляр; GET `/runs/{id}` читает БД новым DbContext; POST `/reserve` изменяет общий ресурс; `/execute` выполняет составную операцию; `/step` выполняет очередной шаг модели саги. Все пути начинаются с `/api/concurrency-lab/database`. API доступен только в Development. Enum в JSON передаётся числом:

| Mode | Значение |
|---|---:|
| Unsafe | 0 |
| Lock | 1 |
| NoTransaction | 2 |
| Transaction | 3 |
| Saga | 4 |

Failure: 0 None; 1 AfterOperation1; 2 BeforeCommit; 3 Points; 4 Loan. Несовместимые пары возвращают 400.

Критическая секция находится в `DatabaseRun.Reserve`: только чтение экземпляра, проверка Available, изменение Available и сохранение выдачи. Барьер, ожидание другого клиента, HTTP и формирование снимка выполняются вне lock. Поскольку `lock` не поддерживает await, внутри используются синхронные вызовы EF. Замок действует для одного учебного экземпляра в одном процессе API; для нескольких реплик нужны средства согласования на стороне БД.

## COMMIT, ROLLBACK и компенсация

Операция 1 добавляет `lab_loans`, операция 2 меняет `lab_copies.Available`. В NoTransaction каждый SaveChanges имеет своё сохранение: после ошибки между ними остаётся выдача свободного экземпляра. В Transaction оба SaveChanges находятся внутри BeginTransactionAsync; CommitAsync сохраняет оба изменения, RollbackAsync отменяет их. Проверяется сохранённое состояние через новый контекст, а не через объекты EF в памяти. Журнал OPERATION 1 внутри BEGIN означает выполненный SQL; окончательное сохранение происходит после COMMIT.

Модель саги выполняет отдельные локальные COMMIT на той же учебной БД, воспроизводя последовательность Catalog/Economy/Lending. Это управляемая демонстрация компенсации; RabbitMQ, outbox/inbox и распределённые отказы здесь не моделируются. Обратные действия — новые записи, а не ROLLBACK предыдущего COMMIT. Дополнительный отказ при создании выдачи иллюстрирует компенсацию двух резервов.

Настоящая Lending Saga продолжает работать через RabbitMQ с отдельными БД сервисов. После Request на странице Discover отображаются её фактический статус, причина отказа, время изменения и ссылка на созданную выдачу. Состояние обновляется каждые 2 секунды до завершения, ошибки связи или срока ожидания. Это индикатор текущего состояния, а не полная история каждого брокерного сообщения.

## Консоль и ошибки

Все API и gateway используют единый формат:

```text
[info] [16:00:00.123 UTC] [DatabaseLabStore] Lab a1b2c3d4 · Client 1 → LOCK · ...
[warn] [16:00:00.130 UTC] [DatabaseLabStore] ... FAIL ...
[error] [16:00:00.140 UTC] [DatabaseLabStore] ... ERROR ...
```

Метка info — голубая, warn — жёлтая, error — красная; цвет отключается при перенаправлении вывода. Русский вывод использует UTF-8. HTTP-поллинг и SQL уровня Information подавлены; сохраняются предупреждения и ошибки. Запуск каждого API даёт одно сообщение готовности. Повторные ошибки подключения outbox/consumer выводятся не чаще раза в 30 секунд, восстановление — отдельным сообщением. Успешный consumer выводит одно сообщение после локального COMMIT с correlation ID.

Настройки: `Logging__Console__Colors=true` принудительно включает ANSI; `Logging__Console__IncludeExceptionDetails=true` добавляет сведения исключения. Для SQL-диагностики `Logging:LogLevel:Microsoft.EntityFrameworkCore=Information` в JSON либо через параметры запуска. По умолчанию длинные stack trace отсутствуют. CLI показывает краткий итог; `--verbose` включает события.

| Ситуация | Реакция |
|---|---|
| Сервер недоступен / тайм-аут | Сообщение клиенту; кнопки снова доступны |
| БД недоступна / неверные реквизиты | 503 с понятным сообщением; сервер и лаборатория в памяти продолжают работать |
| Некорректный JSON, механизм или ClientId | 400 |
| Неизвестный путь, опыт или отсутствующий учебный экземпляр | 404 |
| Повторный клиент, третий запрос, повтор execute, неверный механизм | 409 |
| Единственный ресурс уже занят | FAIL второго клиента с lock; существующая выдача сохраняется |
| Ограничение PostgreSQL (SQLSTATE класс 23) | 409; FK/CHECK дополнительно проверяются тестами |
| Искусственная ошибка / отмена внутри транзакции | ROLLBACK и чтение сохранённого состояния |
| Ошибка при COMMIT | Попытка ROLLBACK; отказ самого отката отмечается RecoveryRequired и возвращается ошибка БД |

Прерывание соединения непосредственно во время физического COMMIT/ROLLBACK отдельно не воспроизводилось. Точка BeforeCommit проверяет искусственный отказ перед COMMIT. После потери связи окончательное состояние нужно повторно прочитать из БД.

Данные опытов сохраняются в PostgreSQL, но реестр опытов и журнал хранятся в памяти API; после перезапуска старый ID недоступен. Экспортировать JSON нужно до остановки API. При создании новых опытов удаляются учебные ресурсы зарегистрированных неактивных опытов старше 2 часов; максимум 200 зарегистрированных опытов. Ресурсы от предыдущего процесса остаются учебными данными в БД.

```powershell
dotnet build Burmalda.slnx -m:1
dotnet test tests/Burmalda.Domain.Tests/Burmalda.Domain.Tests.csproj --no-build
node tools/verify-database-lab.mjs
node tools/verify-lab-ui.cjs

```

Для браузерных проверок нужен пакет playwright и установленный Edge (или `BURMALDA_BROWSER=chrome`). NODE_PATH можно указать на каталог библиотек имеющегося Node runtime. При проверке в этой сессии использован поставляемый с Codex runtime.

Unit-тесты проверяют единственный ресурс, два конкурентных запроса, успешную составную операцию, COMMIT, отсутствие частичного изменения после ROLLBACK, отмену запроса, ограничения FK/CHECK и порядок компенсации. HTTP-harness запускает **два отдельных CLI-процесса**, проверяет PostgreSQL через gateway и повторяет каждый из 10 сценариев дважды. Таблицы формируются из полученных меток времени и состояния БД; неподтверждённые значения не подставляются.
