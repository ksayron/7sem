# ЛР7: Raft и управление PostgreSQL

Burmalda использует собственный Raft на C# для согласования **управляющих операций** над двумя PostgreSQL из ЛР5. Книги, экземпляры, кошельки и остальные бизнес-данные по-прежнему принадлежат PostgreSQL. Голосования перед обычным SQL-запросом нет.

## Запуск ЛР7 + ЛР8

Основной запуск теперь полностью контейнерный:

```powershell
docker compose up -d --build
# http://localhost:5300/raft-lab
./tools/Set-RaftNode.ps1 -NodeId 5 -Action Stop
./tools/Set-RaftNode.ps1 -NodeId 5 -Action Start
```

Пять узлов используют DNS Compose, отдельные тома SQLite и общий том журнала внешних
действий. Управление контейнерами выполняется через Docker Engine API. Web опубликован
через nginx; PowerShell и SDK на хосте для обычного запуска не нужны.

Полная инструкция, текущая архитектура Docker, ограничения и отдельные чек-листы защиты
ЛР7/ЛР8: [единый deliverable](labs-7-8-docker.md). Описания ниже сохраняют детали
протокола и исходного локального режима. Локальные скрипты требуют `-Local`.

## Архитектура

Фасад не участвует в консенсусе. При его отказе недоступна панель, но пять участников продолжают выборы и исполнение ранее согласованных операций. Обычные сервисы используют оба адреса PostgreSQL с `Target Session Attributes=read-write`.

## Реализованный протокол

Основа: [Ongaro, Ousterhout — In Search of an Understandable Consensus Algorithm](https://raft.github.io/raft.pdf).

- Фиксированная конфигурация из пяти участников; большинство всегда три.
- Роли Follower, Candidate, Leader; случайные выборы, term и один устойчиво сохранённый голос в term. ID не даёт приоритета.
- RequestVote проверяет актуальность журнала. AppendEntries проверяет предыдущую запись, исправляет неподтверждённый хвост и не удаляет committed prefix.
- Лидер подтверждает большинство по сохранённым записям; непосредственно продвигает commitIndex только по записям своего term. Новый лидер добавляет no-op.
- Состояние протокола изменяется последовательно. Сеть работает вне этой секции; старые ответы отбрасываются по term и поколению запроса.
- SQLite использует WAL и synchronous=FULL. Изменения hard state, журнала и применённого состояния сохраняются транзакционно до успешного ответа. Ошибка устойчивого хранилища останавливает участника.
- После 256 применённых записей создаётся snapshot. Отставший участник получает InstallSnapshot с атомарной установкой; snapshot включает state machine и дедупликацию команд. Для небольшого локального состояния snapshot передаётся одним RPC.
- Авторитетное чтение требует committed записи текущего term и свежего подтверждения большинства. Lease и предположения о синхронизации часов не используются.
- CommandId сохраняется вместе с исходным содержимым и результатом. Повтор того же запроса не применяет его второй раз; другое содержимое с прежним ID отклоняется.

По умолчанию heartbeat — 200 мс, election timeout — 1500–3000 мс, RPC timeout — 500 мс. Параметры `Raft:HeartbeatMs`, `ElectionMinMs`, `ElectionMaxMs`, `RpcTimeoutMs`, `SnapshotEvery` конфигурируемые. Сохранённые cluster ID, node ID и состав участников должны совпадать с конфигурацией.

## Переключение и внешние эффекты

В журнал попадают начало операции, план source/target, доказательства fencing и WAL, разрешение promotion и подтверждение нового primary. State machine не вызывает Docker. Исполнитель работает только с committed состоянием и сериализует действия общей блокировкой **одного хоста**.

1. Зафиксировать Begin и Planned.
2. Создать устойчивый fencing-маркер старого primary, запретить новые записи и завершить активные клиентские соединения; получить конечный WAL LSN.
3. Зафиксировать SourceFenced; остановить контейнер и подтвердить остановку именно контейнера БД, отдельно от maintenance jobs.
4. Проверить standby, отсутствие paused replay и достижение требуемого LSN.
5. Зафиксировать PromotionAuthorized, выполнить pg_promote, проверить writable роль.
6. Зафиксировать PrimaryActivated и Completed.

Новый лидер продолжает ту же операцию. Смена term не отменяет уже committed разрешение. Перед каждым внешним действием сохраняется намерение; после — результат. Если процесс упал после эффекта, наблюдение PostgreSQL может доказать его завершение без повтора. Сохранившийся дочерний процесс сначала должен завершиться.

Если результат не доказан, операция переходит в NeedsInspection и блокирует другие мутации. Повторная проверка может продолжить её только при доказанном результате. Кнопки «продолжить несмотря на неизвестный исход» нет. Например, утрата конечного LSN после fencing не даёт права произвольно выбрать более старый LSN.

Maintenance-контейнеры имеют имя по OperationId и сохраняются только до подтверждения восстановления. После committed Completed и устойчивого Done в журнале исполнения успешный завершённый контейнер автоматически удаляется без удаления томов. Проверяются имя, метки проекта/операции, признак one-off и exit code. После перезапуска лидер также подбирает оставшиеся завершённые jobs раз в 30 секунд. Активные, ошибочные и неизвестные jobs сохраняются для установления результата; `prune` и принудительное удаление не используются. Журнал участника не разделяется с другими участниками; общий журнал исполнителя не является хранилищем консенсуса.

Блокировка оборудования привязана к корню Compose, даже если изменить каталог данных участников. Устойчиво сохранённый владелец оборудования включает cluster ID и состав Raft: независимая конфигурация не получает право параллельно управлять теми же PostgreSQL.

## Отказы и ограничения

- Один или два отказавших управляющих допускают дальнейшие решения при доступном большинстве. Два оставшихся участника не подтверждают новые команды.
- Сетевая группа из двух может временно считать старый узел лидером, но не может подтвердить новое решение. Интерфейс разделяет локальные роли и авторитетный результат.
- Потеря кворума не останавливает исправный PostgreSQL. Наличие кворума не означает доступность БД и не подтверждает получение её WAL.
- Асинхронная репликация сохранена. При незапланированной потере primary без доказанного fencing и конечного WAL автоматического promotion нет. Нужно безопасно восстановить исходный узел.
- Старый primary возвращается через pg_rewind как standby, без автоматического failback.
- GET и чтение каталога не инициируют promotion. Независимый старый worker не регистрируется. Все инфраструктурные мутации ЛР5 отправляются управляющим узлам.
- Перед первой активацией проверяется старый `authority.json` и незавершённые журналы ЛР5. История не импортируется как записи Raft; неоднозначная миграция блокируется.
- Все пять процессов находятся на одном компьютере. Реализованы отказы процессов и связи, но отказ Docker-хоста остановит весь кластер. Удалённые агенты, динамическое членство и Byzantine-защита не заявляются.
- Это учебная собственная реализация, не сертифицированный промышленный менеджер PostgreSQL. История результатов команд сохраняется без ограничения времени; для длительной эксплуатации понадобится политика клиентских сессий и хранения.

## API и демонстрация

В Development Gateway публикует `/api/raft-lab`: `GET status`, `nodes`, `log?nodeId=&after=&take=`, `events?nodeId=&after=&take=`, `operations/{id}`, `POST operations`. Журналы постраничные; локальные наблюдения снабжены источником и временем.

```json
{"commandId":"новый GUID","kind":"Switchover","node":null}
```

Другие операции: Fence, Stop, Promote, Recover, Pause, Resume, Synchronize. Для Fence/Stop/Recover нужен node `postgres` или `postgres-replica`. `202` означает committed намерение, а не завершение PostgreSQL-команды. При `503 / Unknown` проверьте тот же CommandId; при повторе отправляйте прежнее содержимое и ID.

RPC `/internal/*` не публикуются через Gateway; узлы слушают loopback и проверяют `X-Raft-Key`, а RPC протокола — также cluster ID и отправителя. Локальный ключ задаётся `Raft__InternalKey`; встроенное значение предназначено для этой локальной Development-лаборатории.

Панель показывает term, commit/applied, snapshot, роли, PostgreSQL, этапы операции, события и JSON экспорт. Действия «Остановить» завершают реальные процессы, «Разделить сеть 3+2» изолирует текущего лидера с одним соседом. Диагностическая HTTP-связь при этом сохраняется. «Восстановить связь» снимает delays/drops/partition у доступных узлов.

Для воспроизводимых проверок сбоя между этапами есть Development-only `/internal/executor-fault` с `{"pauseStage":"Planned"}` или `{"pauseStage":"AfterPromotionEffect"}`. Он приостанавливает исполнитель конкретного процесса; остальные участники и протокол продолжают работать. Перезапуск процесса снимает этот тестовый режим.

## Проверки

```powershell
dotnet build Burmalda.slnx -m:1
dotnet test tests/Burmalda.Raft.Tests
dotnet test tests/Burmalda.Domain.Tests
dotnet test tests/Burmalda.LibraryGame.Tests
node tools/verify-raft-lab.cjs
# Playwright должен быть доступен через NODE_PATH:
node tools/verify-raft-ui.cjs
```

Интеграционный verifier создаёт собственные GUID книги/экземпляра, проверяет физические переключения и падения процессов и удаляет только свою fixture. Проверки нельзя запускать параллельно с ручными переключениями или другими изменяющими кластер verifier-ами. Результаты, диагностические JSON и скриншоты: `lab-results/raft-verification`. При неизвестном исходе cleanup сохраняет ошибку, не снимая защиту принудительно.

Проверено 4 ноября 2026: сборка без предупреждений, 109 unit-тестов, 15 сценариев Raft, 12 проверок ЛР5, 33 проверки ЛР6 и 7 браузерных проверок. [Сводка и доказательства](../lab-results/raft-verification/README.md).

Визуальная панель продолжает бумажную палитру, типографику и таблицы Burmalda. Основной сценарий — наблюдение и выполнение лабораторного опыта; роли и состояние БД различаются текстом, таблицы прокручиваются на мобильном экране, действия доступны с клавиатуры.
