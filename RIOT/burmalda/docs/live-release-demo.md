# ЛР10: обновление работающей библиотеки

Демо продолжает пульт ЛР9: реальные читатели, HPA, Pod, Prometheus и Grafana.
Новый сценарий удерживает нагрузку во время Jenkins Pipeline. Кнопка
«Выпустить обновление» увеличивает `ReleaseEdition.Number` в настоящем C#-файле,
создаёт commit в отдельной ветке `demo/live-release`, отправляет его в GitHub
и запускает Jenkins. Основная рабочая копия и ветка master этим действием не меняются.
Jenkins обнаруживает push через Poll SCM; ожидание перед Checkout — до двух минут.

## Подготовка

Нужны работающая базовая ЛР10, Windows Git с настроенным доступом на push,
Python, PowerShell и Docker Desktop Kubernetes. Команды из `RIOT/burmalda`:

```powershell
./tools/LiveRelease.ps1 Prepare
./tools/LiveRelease.ps1 Build
./tools/LiveRelease.ps1 Start
```

Prepare создаёт отдельную sparse-копию исходников в игнорируемом
`.artifacts/live-release/source` и публикует демонстрационную ветку. Повторный
запуск сохраняет редакцию и объединяет с ней текущий **закоммиченный** код проекта.
Незавершённые изменения в отдельной source-копии блокируют подготовку.
Build собирает только обновлённый пульт; прикладные образы
собирает Jenkins. Start поднимает мониторинг, включает HPA с минимумом двух
Catalog/Gateway, сохраняет текущие прикладные образы и настраивает завершение Pod.
Первичная настройка выполняется до запуска измеряемой нагрузки.

- Библиотека: <http://localhost:30530>.
- Пульт: <http://localhost:5310>, обычный администратор Burmalda.
- Jenkins: <http://localhost:8081/job/burmalda-lab10/>.
- Grafana: <http://localhost:3000/d/burmalda-demo>.

Вход в библиотеку идёт через NodePort Service `web-live`, поэтому соединение
не привязано к одному Pod, как у port-forward. Пульт и Grafana по-прежнему
используют port-forward и не входят в восемь обновляемых компонентов Pipeline.

Jenkins переключается на `demo/live-release`. Дождитесь окончания первичной
сборки: она устанавливает исходную редакцию с заголовками версии. При необходимости
посмотрите `./tools/LiveRelease.ps1 Status`.

## Сценарий показа

1. В пульте выбран сценарий «Обновление работающей библиотеки»: по умолчанию
   60 клиентов, рост 30 с и удержание 1200 с. Это запас на реальную сборку,
   длительность которой зависит от ресурсов и кэшей компьютера.
2. Подготовьте клиентов и запустите сценарий. 90% читают каталог, 10% выполняют
   выдачу/возврат тестовых экземпляров. Дождитесь выхода на стабильную нагрузку.
3. Откройте библиотеку рядом и нажмите «Выпустить обновление» в пульте.
4. Наблюдайте новый SHA и Checkout → Restore → Build → Test → Load → Package →
   Deploy → Verify. До Deploy продолжает работать прежний выпуск.
5. Во время Deploy видны старые, новые Ready и завершающиеся Pod. В ответах
   Catalog появляются новый SHA и следующая редакция. Счётчики учитывают реальные
   запросы и ошибки за окно Deploy до завершения Pipeline; результаты сохраняются
   в `GET /api/demo/releases/{номер-сборки}`.
6. После SUCCESS продолжите пользоваться библиотекой, затем завершите нагрузку
   кнопкой «Завершить операции и остановить». Если остались неизвестные исходы,
   используйте существующую проверку и завершение операций пульта.

Для повторного показа кнопка создаёт следующую редакцию. Пока выполняется выпуск
или исходники отправляются в Git, повторная команда отклоняется. Ошибка push
показывается отдельно от статуса Jenkins; секреты в состояние пульта не попадают.

## Что обеспечивает обновление

Deployment использует RollingUpdate, `maxSurge: 1`, `maxUnavailable: 0` и readiness
probes. Pipeline меняет шаблон, сохраняя число реплик под управлением HPA.
PreStop даёт десять секунд на распространение удаления endpoint, после чего
ASP.NET завершает начатые запросы; grace period — 45 секунд. Обновления не меняют
схемы БД и контракты между одновременно работающими версиями.

График и счётчик ошибок показывают измеренный результат этого запуска. Ноль
ошибок на выборке не гарантирует отсутствие простоев при любых изменениях:
совместимость версий, ёмкость узла, readiness и корректное завершение нужны вместе.
Пропущенное начало наблюдения и отсутствие запросов обозначаются в пульте явно.

Фактические результаты проверки приведены в
[журнале живого обновления](../lab-results/live-release-verification/README.md).

Локальный мост `tools/ci/release-bridge.py` предоставляет только очищенное состояние
одного Jenkins job и фиксированное действие выпуска. Ключ моста хранится в Secret;
Git и пароль Jenkins остаются на Windows. Произвольных команд, URL и путей API нет.

## Остановка и возврат

```powershell
./tools/LiveRelease.ps1 Stop
# Остановлены нагрузки Kubernetes, мост и Jenkins. Данные и история сохранены.

# Для базовой ЛР10 без демо:
./tools/Jenkins.ps1 Prepare
./tools/Jenkins.ps1 Start -Branch master
./tools/Jenkins.ps1 Run
```

Не запускайте `Jenkins.ps1 Prepare` одновременно с активным демо: он возвращает
базовую конфигурацию телеметрии. Для обычного повтора показа достаточно Start,
подготовки клиентов и кнопки выпуска; не удаляйте PVC, Secret и source-копию.
