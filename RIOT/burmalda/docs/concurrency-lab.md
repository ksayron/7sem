# Лаборатория конкурентности Burmalda: ЛР 2 и ЛР 3

Демонстрационный сервис моделирует несколько клиентов, которые резервируют **один и тот же виртуальный экземпляр книги**. У него нет подключения к БД, RabbitMQ и реальному каталогу. Состояние каждого эксперимента хранится в памяти одного процесса 30 минут; новая попытка создаёт новый счётчик. Преднамеренно ошибочный API доступен только при `ASPNETCORE_ENVIRONMENT=Development`.

## Как запустить

Для лаборатории не нужны Docker и остальные сервисы Burmalda. Откройте три терминала в корне проекта:

```powershell
dotnet run --project src/Services/ConcurrencyLab/Burmalda.ConcurrencyLab.Api
dotnet run --project src/Gateway/Burmalda.Gateway
dotnet run --project src/Clients/Burmalda.Web
```

Затем откройте `http://localhost:5300/concurrency-lab`. В Visual Studio сервис включён в профили **All backend services** и **Full application**. Сервис слушает порт 5107, gateway — 5000, веб-клиент — 5300.

Gateway применяет к лабораторному маршруту отдельный лимит 400 запросов в минуту; бизнес-маршруты сохраняют прежние 120 запросов в минуту. Это позволяет пройти опыт с 32 клиентами во всех четырёх сериях. Настройка использует [политику YARP для конкретного маршрута](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/yarp/rate-limiting?view=aspnetcore-9.0).

Страница сначала делает последовательный контрольный прогон, затем сравнивает три независимых конкурентных эксперимента с одинаковым числом запросов и паузой между чтением и записью. Отдельный запрос обозначает отдельного клиента; каждый запрос проходит gateway к одному серверному процессу. В конкурентных опытах стартовый барьер пропускает первые четыре запроса к счётчику вместе. Он нужен для повторяемости опыта при разных ограничениях HTTP-соединений и **не защищает** общий ресурс.

Для терминального прогона с сохранением полного журнала:

```powershell
dotnet run --project tools/ConcurrencyLab.Client -- compare 12 60
dotnet run --project tools/ConcurrencyLab.Client -- clock 90000 -45000
```

Команды сохраняют JSON с параметрами и результатами в `lab-results/` текущего каталога. По умолчанию CLI обращается прямо к сервису на `http://localhost:5107`; переменная `BURMALDA_LAB_URL` позволяет указать адрес gateway. Чтобы показать **два отдельных клиентских процесса**, сначала создайте эксперимент:

```powershell
dotnet run --project tools/ConcurrencyLab.Client -- create Unsafe 12 60
```

Скопируйте выведенный GUID. Почти одновременно выполните в терминалах A и B:

```powershell
dotnet run --project tools/ConcurrencyLab.Client -- join "GUID" 6 A
dotnet run --project tools/ConcurrencyLab.Client -- join "GUID" 6 B
```

После завершения обоих клиентов вызовите `dotnet run --project tools/ConcurrencyLab.Client -- report "GUID"`. Для защищённых режимов повторите `create` с `Lock` и `SemaphoreSlim`. Все три режима работают с одним API-контрактом и одинаковой нагрузкой.

## ЛР 2: параллельная обработка и Race Condition

`Process` — экземпляр запущенной программы; у API и у каждого CLI-клиента разные PID. `Thread` — поток выполнения внутри процесса. `Task` — единица асинхронной работы в .NET: после `await` продолжение может исполняться другим потоком. Поэтому один `ThreadId` не равен одному клиенту и смена `ThreadId` сама по себе не доказывает параллелизм.

В последовательном контрольном опыте без `lock` второй запрос начинает чтение после записи первого, поэтому все 12 обновлений сохраняются. В конкурентном запуске интервалы запросов перекрываются (`MaxConcurrentRequests > 1`). В журнале `started`, `read`, `wrote` есть UTC-время, номер запроса, клиент, значение и серверный `ThreadId`. Запросы с одинаковым прочитанным значением до первой записи демонстрируют гонку; `ExpectedReservations - ActualReservations` показывает потерянные обновления.

Режим `Unsafe` выполняет намеренно неправильный `read → await Task.Delay → write` без критической секции. Например, если четыре клиента прочли `0`, все четыре могут записать `1`, хотя успешно завершились четыре запроса. Это **Lost Update**, а не ошибка самих `Task` или `async`.

## ЛР 3: критическая секция и часы

Оба исправленных режима защищают всю операцию `read → work → write`:

| Режим | Механизм | Что видно в опыте |
| --- | --- | --- |
| `Lock` | `lock` и короткая синхронная пауза внутри секции | Все обновления сохранены; ожидающие запросы занимают серверные потоки. |
| `SemaphoreSlim` | `WaitAsync` / `Release` и `Task.Delay` внутри секции | Все обновления сохранены; ожидание и пауза не удерживают поток. |

`MaxConcurrentRequests` считает запросы, вошедшие в обработчик, включая ожидающие замок. Он не означает, что защищённые записи выполнялись одновременно. В таблице `read`/`wrote` видно, что для защищённых режимов следующая операция читает результат предыдущей. Пауза в критической секции делает цену сериализации заметной. Абсолютное время зависит от машины и не служит доказательством корректности.

`lock` и `SemaphoreSlim` синхронизируют только потоки **одного процесса API**. Они не согласуют несколько реплик сервиса и не заменяют атомарные обновления/транзакции БД. Производственный каталог Burmalda уже использует атомарное условное изменение состояния экземпляра; учебный счётчик не является его реализацией.

Для часов клиент сохраняет локальные отметки `t₀` перед запросом и `t₃` после ответа. Сервер возвращает `t₁` при получении и `t₂` перед отправкой. Можно задать смещение обоих часов и время обработки на сервере. Оценки:

```text
offset = ((t₁ - t₀) + (t₂ - t₃)) / 2
network RTT = (t₃ - t₀) - (t₂ - t₁)
corrected client time = t₃ + offset
```

Из пяти проб выбирается минимальный RTT. При клиентском сдвиге `+90000` мс и серверном `-45000` мс ожидаемый `offset` близок к `-135000` мс. Это программная коррекция времени в клиенте, а не изменение системных часов. Асимметричная сеть и планировщик могут вносить ошибку; сравнивать события разных узлов по сырым локальным отметкам нельзя.

## Зафиксированный локальный прогон

24 сентября 2026 года при 12 запросах и паузе 60 мс получено:

| Режим | Ожидалось | Получено | Потеряно | Пик запросов | Время |
| --- | ---: | ---: | ---: | ---: | ---: |
| `Unsafe`, по очереди | 12 | 12 | 0 | 1 | 810 мс |
| `Unsafe`, одновременно | 12 | 1 | 11 | 12 | 2102 мс |
| `Lock`, одновременно | 12 | 12 | 0 | 12 | 799 мс |
| `SemaphoreSlim`, одновременно | 12 | 12 | 0 | 12 | 826 мс |

Время `Unsafe` в этом запуске включает разогрев HTTP-клиента и сервера; сравнивать режимы следует по корректности и событиям, а для времени делать несколько прогретых повторений. Полный машинный журнал доступен в [образце JSON](../lab-results/concurrency-lab-20260924-182306.json). При сдвигах `+90000`/`-45000` мс CLI оценил `offset` как `-135000.3` мс и сетевой RTT как `1.5` мс; [все пять временных проб](../lab-results/clock-20260924-181459.json) сохранены отдельно.

Проверен и верхний предел через gateway: 32 последовательных операции дали `32/32`, конкурентный `Unsafe` — `2/32`, `Lock` и `SemaphoreSlim` — `32/32`. [Журнал прогона 32 клиентов](../lab-results/concurrency-lab-20260924-182836.json) содержит все события.
