# Демонстрация нагрузки и восстановления Burmalda

ЛР9 с демонстрацией сдана 13 ноября 2026 года. После сдачи стенд остановлен через
`./tools/Kubernetes.ps1 Stop -Demo`: Pod завершены, локальные port-forward закрыты,
PVC с данными PostgreSQL, RabbitMQ, пульта и Prometheus сохранены.

Демо расширяет основной Kubernetes-стенд, сохраняя PostgreSQL, RabbitMQ и их PVC.
Catalog масштабируется от 1 до 4 Pod, Gateway — от 1 до 3. Симулятор не имеет прав
масштабирования; количество реплик определяет HPA по CPU с целью 60% от request.
Это несколько экземпляров на одном компьютере, без расширения числа узлов.

## Запуск

Команды из корня `burmalda`, PowerShell 7.4+, контекст `docker-desktop`:

```powershell
# При нехватке памяти сначала остановить текущие Pod. Данные сохранятся.
./tools/Kubernetes.ps1 Stop
./tools/Kubernetes.ps1 Prepare -Demo
./tools/Kubernetes.ps1 Build -Demo
./tools/Kubernetes.ps1 Start -Demo
./tools/Kubernetes.ps1 Access -Demo -Background
./tools/Kubernetes.ps1 Status -Demo
```

- Библиотека: http://localhost:5300
- Пульт: http://localhost:5310 — существующий администратор `admin@burmalda.local`.
- Grafana: http://localhost:3000/d/burmalda-demo — просмотр готового дашборда без входа.

Пароль администратора находится в локальном `.artifacts/k8s/secret.json`,
`stringData.ADMIN_PASSWORD`; не копировать его в отчёт. Отдельный demo-Secret содержит
пароль тестовых аккаунтов, ключ внутреннего управления и пароль администратора Grafana.
Пароли и токены не входят в ответы состояния и публичные результаты. Сессии тестовых
клиентов на PVC защищены ASP.NET Data Protection; ключи сохраняются на том же PVC.

Сборка последовательная: параллельная публикация всех .NET-образов перегружает этот
16-ГиБ хост. Пока сборка работает, дополнительные копии Compose запускать не нужно.
Prometheus хранит до 24 часов / 1 ГБ метрик на отдельном PVC. Настройки Grafana
поступают из ConfigMap, её локальные ручные изменения не являются источником истины.

## Подготовка и показ

1. На пульте выбрать пик и нажать «Подготовить клиентов». Для первого запуска
   создаются отдельные аккаунты; анонимные запросы идут не быстрее 90/мин при лимите
   Gateway 120/мин. Это отдельный подготовительный этап, он может занять несколько минут.
2. После готовности выбрать «Восстановление под нагрузкой», рост 90 с, удержание 120 с.
3. Открыть рядом библиотеку и Grafana. Запустить сценарий и наблюдать готовые/желаемые
   реплики, CPU, реальные ответы HTTP и состояния Pod.
4. На третьей минуте удаляется один Catalog Pod, только если готовы минимум два.
   Через 30 секунд включается 25% ответов 503 на 30 секунд. Затем клиенты уходят.
5. После снижения CPU HPA уменьшает число экземпляров. В журнале удаление Pod,
   создание замены, Ready и истечение API-сбоя обозначаются отдельными событиями.

Изменение целевого числа клиентов переводит нагрузку в ручной режим. Кнопка плавного
снижения уменьшает её за 30 секунд и оставляет три минуты для наблюдения. Обычная
остановка ждёт уже начатые операции; аварийная прерывает запросы и снимает сбои.
После закрытия браузера нагрузка продолжает работать. Перезапуск симулятора отмечает
запуск как `interrupted`, сохраняет неизвестные результаты и не возобновляет нагрузку.

Смешанный сценарий использует 10% клиентов для выдачи/возврата, остальных — для чтения.
Книга и экземпляр создаются для каждой группы из десяти клиентов и используются
повторно. Нет автоматического повтора изменяющего HTTP-запроса при неизвестном исходе.
Оставшиеся операции отображаются на пульте. После остановки можно выполнить
«Проверить и завершить оставшиеся операции»: читается фактический статус и выполняется
допустимая отмена либо возврат; окончательное освобождение подтверждается проекцией
не ранее трёх минут после остановки. Чужие книги и аккаунты не удаляются.

## Что означают сбои

Удаление Pod запускает его замену контроллером Deployment. Новый экземпляр имеет новый
UID; это отличается от перезапуска контейнера внутри прежнего Pod.

Ошибка API не останавливает процесс. Она временно меняет ответы всем клиентам Catalog
или Gateway и автоматически истекает максимум через 120 секунд. Health probes,
внутреннее управление и статические ресурсы исключены. Экземпляры опрашивают пульт
каждые 2 секунды и локально проверяют абсолютный срок; потеря связи с пультом не
продлевает сбой. Новый процесс пульта начинает с выключенными сбоями.

Доступ к Kubernetes ограничен namespace `burmalda`: чтение Pod, Deployment, ReplicaSet,
HPA и удаление Pod. Backend дополнительно проверяет UID и цепочку владельцев до
Catalog/Gateway. Для Prometheus отдельно разрешено чтение kubelet через `nodes/proxy`.
Vendored metrics-server 0.8.0 имеет локальный `--kubelet-insecure-tls` для сертификата
Docker Desktop kubeadm; эта конфигурация не предназначена для production.

## Проверка

```powershell
dotnet test tests/Burmalda.DemoControl.Tests/Burmalda.DemoControl.Tests.csproj
node tools/verify-demo.cjs
node tools/verify-demo-safety.cjs
node tools/verify-demo-ui.cjs
node tools/verify-core.cjs
```

`verify-demo.cjs` проверяет ограничения управления, подготавливает клиентов и проходит
полный семиминутный сценарий. Требует работающих port-forward. Число клиентов:
`$env:BURMALDA_DEMO_CLIENTS='300'`. Для отдельных этапов:
`$env:BURMALDA_DEMO_PHASE='checks'`, `'prepare'` или `'run'`; без переменной выполняется всё.
Публичные результаты — `lab-results/demo-verification`, без JWT и паролей.

`verify-demo-safety.cjs` выполняет смешанные операции и перезапускает только DemoControl,
проверяя локальное истечение сбоя при недоступном пульте и сохранность SQLite.
Запускать отдельно от основного сценария. Для проверки интерфейса нужен установленный
Microsoft Edge и Playwright: `npm install --prefix .artifacts/browser playwright`.
`verify-demo-ui.cjs` проверяет вход с клавиатуры, CSRF, настольную/мобильную компоновку
и сохраняет скриншоты. Состояние реальной приёмки описано в
`lab-results/demo-verification/VALIDATION.md`.

Успешный показ требует фактического роста и снижения **обоих** сервисов, замены Pod,
истечения ошибки и свежих метрик. При отсутствии роста не имитировать его командами:
проверить metrics API, условия HPA, фактический CPU, распределение соединений и
ресурсы генератора/узла. Порог задержек по умолчанию p95 ≤ 1 с, ошибок < 1%.
Наибольший наблюдённый успешный RPS относится только к данному сценарию и компьютеру.

Проверенный пресет этого компьютера: 300 клиентов, рост 90 с, удержание 120 с.
Наблюдались 4 Catalog / 3 Gateway и 150,4 успешных RPS в здоровом 30-секундном окне.
Сценарий завершается на 7:00; последнее уменьшение HPA в проверке завершилось к 7:33.
Для показа с запасом выделить восемь минут. Это наблюдение, а не предел мощности узла.

## Остановка

```powershell
./tools/Kubernetes.ps1 Stop -Demo
```

HPA удаляются перед остановкой Deployments, port-forward закрываются. Namespace,
Secret и PVC остаются. metrics-server как кластерный компонент не удаляется.
Для возврата к обычной среде запустить `Start` без `-Demo`; для демо — `Start -Demo`.
